Writing good prompts

The quality of what Build Agent builds depends on the quality of your brief. Treat it like a capable developer who's just joined your team: it knows the platform well, but it only knows your problem from what you tell it.

The good news: if you've completed your planning template, you've already written most of your brief. This guide shows you how to turn it into prompts, using a worked example.

Six habits that work

1. Be comprehensive. One detailed prompt beats several vague ones. Include the tables, fields, roles and automation you need in a single prompt.

2. Use platform terms where you can. Say "a reference field to sys_user" rather than "a field for who ordered it". Naming tables, fields, roles and record types gets you a more accurate first attempt. Conversational prompts are fine early on; get more precise as you build.

3. Plan first for anything complex. Ask Build Agent to create a plan before it builds. Review it as a team, then approve.

4. Let it interview you. If something is still unclear, ask Build Agent to ask you questions first. This works better than guessing at details.

5. Draft offline. Write your prompt in a text editor or shared doc, refine it as a team, then paste it in.

6. One feature per conversation. Build and test one feature, then start a new conversation for the next. Long conversations that try to do everything get confused.

From plan to prompts

Each section of your planning template feeds a different prompt. Work through them in this order:

Order Prompt Built from template section New conversation?
1 Review the plan The whole template Yes
2 Build the foundation: data and roles 2, 5, 9 Yes
3 Add the process 6 Yes
4 Add the rules 7 Yes
5 Add notifications 6 Same as 4, or new
6 Shape the user experience 8 Yes
7 Create test data 10 Same as 6, or new
8 Test the scenarios 10 Yes
9 onwards Add a skill or an agent 13 Yes (Guide 5)

Sections 1, 3, 11 and 12 (the problem, the finished product, value and risks) don't become features. They give Build Agent context in prompt 1, and they become your pitch.

Tip

Studio or IDE? In ServiceNow Studio, paste the relevant parts of your plan straight into the chat. If your team is using the ServiceNow IDE, you can also save your plan as a Markdown file in your project and ask Build Agent to use it as context throughout the session.

Worked example: Workplace Issue Reporter

Here's a completed planning template for an example app, followed by the prompts that build it. Guide 5 continues the same example by adding an AI skill and agent. Use it as a model for your own.

The completed plan

1. The problem Employees report office problems such as broken lights, faulty desks and heating failures by email, chat messages or by stopping someone in the corridor. Reports get lost, the same problem is reported five times, and nobody knows whether anything is happening. The facilities coordinator spends the first hour of every day reading and forwarding messages. In one sentence: Office problems are reported in too many places, so they're slow to reach the right team and people never hear back.

2. The people

Role What they need to do How often
Reporter (any employee) Report a problem, check its progress, hear when it's fixed Occasionally
Fixer (member of a facilities team) See issues for their team, update progress, resolve them Daily
Coordinator Review new issues, correct category or priority, manage teams Daily

3. The finished product Headline: Anyone can report an office problem in 30 seconds, and it reaches the right team without anyone sorting an inbox. Demo story:

  1. Alex notices the heating isn't working in meeting room 3B and reports it in a couple of sentences.

  2. The issue is categorised as Heating and cooling, marked High priority, and routed to the Building services team. Two similar reports from the same floor are flagged as possible duplicates.

  3. Jordan in Building services picks it up, fixes it, and resolves it with a note.

  4. Alex gets a notification that it's fixed.

4. Scope

Must have (day 1) Should have (day 2) Won't have
Issue table, report form, routing by category, resolve with notes Notifications, "My issues" list, coordinator and team views, AI triage skill and agent Mobile app, building management system integration, reporting dashboards

5. Data

Issue

Field Type Choices or referenced table Mandatory?
Number Auto-number (prefix WPI) Yes
Short description Text Yes
Description Long text Yes
Location Reference cmn_location Yes
Category Choice Electrical, Plumbing, Heating and cooling, Furniture, Cleaning, Other No (set during triage)
Priority Choice 1 - Urgent, 2 - High, 3 - Normal, 4 - Low (default Normal) Yes
State Choice New, Assigned, In progress, On hold, Resolved, Closed Yes
Reported by Reference sys_user (default: current user) Yes
Assignment group Reference sys_user_group No
Assigned to Reference sys_user No
Resolution notes Long text When resolved
Work notes Journal No

Category routing

Field Type Choices or referenced table Mandatory?
Category Choice Same choices as on Issue Yes
Assignment group Reference sys_user_group Yes

Relationship: Each category routes to one assignment group. Many issues can share a location.

6. The process

  • Trigger: A reporter submits an issue. It starts in the New state.
  • Steps: When a category is set, the issue is assigned to that category's group and moves to Assigned. A fixer sets it to In progress, then to Resolved with resolution notes. The reporter can confirm the fix to close it; the coordinator can also close it.
  • States: New → Assigned → In progress → (On hold) → Resolved → Closed.
  • Notifications: The reporter when the issue is resolved; the coordinator straight away for anything Urgent; the assignment group when an issue is assigned to them.

7. Rules and logic

  • When the category is set or changed, set the assignment group from the Category routing table and set the state to Assigned.
  • Never allow an issue to be resolved without resolution notes.
  • Assigned to must be a member of the assignment group.
  • Reporters can't change the priority, category or assignment.

8. Where people work

  • Reporters: a short report form (short description, description, location) and a "My issues" list.
  • Fixers: a list of open issues assigned to their groups.
  • Coordinator: a list of New issues, and all open issues grouped by location.

9. Who can see and do what

Role Create Read Update Delete
Reporter Issues Own issues Own issues: description only, and confirming a fix None
Fixer None All issues Issues assigned to their groups None
Coordinator Issues, Category routing All All issues and Category routing Category routing

10. Test scenarios

Scenario Expected result
Report an issue as a reporter Issue created as New; appears in the coordinator's list
Coordinator sets the category to Plumbing Assigned to Building services; state is Assigned
Fixer resolves an issue with no resolution notes Blocked with a clear message
Report an Urgent issue Coordinator notified straight away
Reporter tries to change the assignment group Not allowed

11. How you'll show value We'd measure time from report to assignment (currently up to a day), the number of duplicate reports, and how often people chase for updates.

12. Assumptions and risks Assumes each category maps to one team. Location data already exists on the platform. Integration with building systems is out of scope.

13. Where could AI help?

Where people spend time today What AI could do Skill or agent? What a person stays in control of
The coordinator reads every new report to choose a category and priority Read the description and suggest a category, priority and one-line summary Skill The coordinator can change any suggestion
Several people report the same problem Find similar open issues at the same location and flag possible duplicates Agent (uses the skill) The coordinator decides whether to merge or close duplicates

The prompts

Here's how the team turns that plan into prompts. Notice how each prompt copies wording straight from the template.

Prompt 1: Review the plan

Start here. Paste in your whole plan and ask Build Agent to check it before anything is built.

Prompt
We're building an app at a hackathon. Below is our team's plan.
Don't build anything yet.

Please:
1. Summarise what you understand we want to build.
2. Point out any gaps, contradictions or risks in the plan.
3. Ask us any questions you need answered, one at a time.
4. Suggest the order we should build it in, one feature per step.

[Paste your completed planning template here]

Answer its questions, update your template with anything you've learned, and then mark this conversation complete.

Prompt 2: Build the foundation (data and roles)

Prompt
Create a scoped app called Workplace Issue Reporter.

Purpose: let employees report office problems in one place and route
them to the right facilities team.

Roles:
- workplace_reporter: can create issues and read their own issues.
- workplace_fixer: can read all issues and update issues assigned to
  their groups.
- workplace_coordinator: can read and update all issues, and manage
  the Category routing table.

Tables:
1. Issue, with fields:
   - Number (auto-number with prefix WPI)
   - Short description (string, mandatory)
   - Description (long string, mandatory)
   - Location (reference to cmn_location, mandatory)
   - Category (choice: Electrical, Plumbing, Heating and cooling,
     Furniture, Cleaning, Other)
   - Priority (choice: 1 - Urgent, 2 - High, 3 - Normal, 4 - Low;
     default 3 - Normal)
   - State (choice: New, Assigned, In progress, On hold, Resolved,
     Closed; default New)
   - Reported by (reference to sys_user, default current user)
   - Assignment group (reference to sys_user_group)
   - Assigned to (reference to sys_user)
   - Resolution notes (long string)
   - Work notes (journal input field, visible to fixers and coordinators)
2. Category routing, with fields:
   - Category (same choices as Issue, mandatory, unique)
   - Assignment group (reference to sys_user_group, mandatory)

Set up access controls to match the roles above.
Create a plan first and wait for my approval before building.

What's happening: This uses sections 2, 5 and 9. The roles and tables are the foundation, so build and check them before adding any behaviour. Open both tables and check the fields before moving on.

Prompt 3: Add the process

Prompt
In the Workplace Issue Reporter app, add the issue process:

- New issues start in the New state.
- When the Category is set or changed, look up the Assignment group
  in the Category routing table, set it on the issue, and set the
  State to Assigned.
- Fixers can move an issue to In progress, On hold or Resolved.
- The reporter can confirm a Resolved issue is fixed, which sets the
  State to Closed. The coordinator can also close Resolved issues.

Don't change the table structure. Show me the plan before making changes.

What's happening: This uses section 6. The "Don't change..." line protects the foundation you've already tested.

Prompt 4: Add the rules

Prompt
In the Workplace Issue Reporter app, add these rules to the Issue
table. Each should stop the record being saved and show a clear
message to the user:

1. Never allow an issue to be set to Resolved without Resolution notes.
2. Assigned to must be a member of the Assignment group.
3. Users with only the workplace_reporter role can't change Priority,
   Category, Assignment group or Assigned to.

Show me the plan before making changes.

What's happening: Section 7, copied almost word for word. Writing rules as sentences in the template makes this step easy.

Prompt 5: Add notifications

Prompt
In the Workplace Issue Reporter app, add these notifications:
- Email the Reported by user when their issue is Resolved, including
  the Resolution notes and a reminder to confirm the fix.
- Email users with the workplace_coordinator role as soon as an issue
  is created or changed to 1 - Urgent.
- Email the Assignment group when an issue is assigned to them.

Prompt 6: Shape the user experience

Attach the photo of your screen sketches to this prompt.

Prompt
In the Workplace Issue Reporter app, improve the experience for each
role. I've attached our sketches.

For reporters:
- A short report form with only Short description, Description and
  Location.
- A "My issues" list showing their issues, newest first, with State.

For fixers:
- A list of open issues assigned to their groups, highest priority
  first.

For coordinators:
- A list of New issues.
- All open issues grouped by Location.

Show me the plan before making changes.

What's happening: Section 8. Sketches and screenshots help Build Agent match what you have in mind.

Prompt 7: Create test data

Prompt
Create sample data for the Workplace Issue Reporter app so we can
test it. Use fictional names and values only.

- 3 assignment groups: Building services, Workplace team and
  Cleaning services.
- Category routing records: Electrical, Plumbing and Heating and
  cooling to Building services; Furniture and Other to Workplace team;
  Cleaning to Cleaning services.
- 3 locations, if none exist.
- 4 test users: 2 with workplace_reporter, 1 with workplace_fixer (a
  member of Building services) and 1 with workplace_coordinator.
- 15 issues across every State and Category, written the way real
  people describe problems. Include 3 issues about the same heating
  problem at the same location, and a few with no Category yet.

What's happening: The realistic descriptions and the deliberate duplicates matter. They're what the AI skill and agent in Guide 5 will work on.

Prompt 8: Test the scenarios

Prompt
Here are our test scenarios for the Workplace Issue Reporter app:

[Paste the table from section 10 of your plan]

For each scenario, tell us how to test it manually step by step,
including which test user to log in as. Then suggest automated tests
we could add.

What's happening: Section 10. Run through each scenario yourself. If one fails, describe what happened in a new prompt, or roll back to a checkpoint (see Guide 4).

Day 2: building on what works

Once your "must have" scope is working and tested, move on to your "should have" list, one feature per conversation, using the same pattern as Prompt 3:

Prompt
In the [App name] app, add [feature from your "should have" list].
It should [expected behaviour].
Don't change [anything that must stay as it is].
Show me the plan before you make changes.

When the core app works, continue to Guide 5 to add AI.

More useful prompts

When you're not sure how to describe something:

Prompt
I want to [goal]. Suggest the ideal prompt I should give you to build
this, and tell me about any common pitfalls.

When a part of your plan is still fuzzy:

Prompt
We want the app to [rough idea]. Before you plan anything, interview me.
Ask one question at a time until you understand what we need, then
summarise it back to me.

When something on screen looks wrong: attach a screenshot.

Prompt
Here's a screenshot of [page or form]. [What's wrong, e.g. the Location
field should be at the top, and the Description field is missing].
Please fix this.

When you want to understand what was built:

Prompt
Explain how the [feature] in this app works, which records you created
for it, and where I can find them.
